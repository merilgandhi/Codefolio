# Public contact form and Nodemailer delivery

Verified locally on 2026-10-25. Both public portfolio layouts include a **Contact** navigation link and the same responsive React Hook Form contact section. Two real tests were sent: the initial delivery check and a separately approved email-design check. The owner confirmed Inbox delivery and the redesigned appearance in Gmail.

## Request flow and privacy

1. A visitor supplies their name, reply email, subject and message on `/:username`.
2. `POST /api/contact/:username` checks request origin/marker, JSON format, limits and validated fields.
3. The backend validates the username and queries MongoDB for that account's private registered email. Request bodies cannot supply `to`, `from`, envelopes, attachments or account selectors.
4. Nodemailer sends from the application's configured sender, to that one saved recipient. The visitor's address is used as **Reply-To**, so the owner can reply directly.
5. The API returns a generic success only after SMTP accepts that recipient. A provider error produces a sanitized 503 response. SMTP acceptance does not by itself prove inbox receipt; the real inbox confirmation above supplies that evidence.

The public document, public JSON and contact responses do not expose the owner's email, SMTP settings or provider error details. Messages contain branded HTML generated by the server and a complete plain-text alternative. Visitor content is escaped before insertion into the HTML. URL/file content access is disabled, and the SMTP envelope is limited to one recipient. A visitor's name/email/subject/message is transmitted to the chosen portfolio owner; the form explains this before submission. Contact messages are not stored in MongoDB or logged by the production transport.

The form appears only on the public page. Private draft previews do not contain a sending form or a broken Contact anchor. Saved portfolio data and the owner's session are unchanged by this milestone.

## Email design

`server/mail/contactEmail.js` renders the HTML and text versions. The HTML uses a CodeFolio wordmark, muted violet accents, a prominent subject, sender initials/name/address, a separate message card, a reply button and a compact portfolio footer. Paragraphs and line breaks are preserved without truncating the message. The reply button encodes the validated visitor address and subject; the normal email Reply action also works through Reply-To.

The self-contained email uses presentation tables, inline styles and a mobile media query, with no external fonts, images or tracking assets. Its card is capped at 640px and adapts to a narrow reading pane. Gmail's supported styles and media queries are documented in [Google's CSS reference](https://developers.google.com/workspace/gmail/design/css).

Browser previews passed at 320, 390, 760 and 1280px with no horizontal overflow. The owner confirmed the actual new message had the branding, message card and reply button and looked good in Gmail. Other email applications have not been manually checked; their rendering may differ. The plain-text alternative is retained for clients that do not display HTML.

## Gmail setup

Nodemailer is the sending library; Gmail supplies the SMTP server. One application sender serves all portfolios. Each portfolio's registered account email determines its recipient.

Enable Google 2-Step Verification, then create an App Password named **CodeFolio** in [Google App Passwords](https://myaccount.google.com/apppasswords). See [Google's instructions and account restrictions](https://support.google.com/accounts/answer/185833). The user completes this credential setup themselves.

Keep the values in the ignored local `.env` file:

```dotenv
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_USER=youraddress@gmail.com
SMTP_PASS=your16characterapppassword
SMTP_FROM=
```

Remove display-group spaces from the App Password. Leave `SMTP_FROM` empty to use `SMTP_USER`, or set a sender address permitted by the provider. Credentials must never use a `VITE_` prefix or be committed. Restart the API after changing `.env`.

Port **587 with required STARTTLS** was verified on this connection. The initial port 465 check failed to connect; 587 authenticated successfully. The transport also supports direct TLS on 465. Certificate verification is retained. See Nodemailer's [SMTP configuration](https://nodemailer.com/smtp) and [message/Reply-To configuration](https://nodemailer.com/message).

## Validation and abuse controls

- Name: 1–100 characters; one line.
- Reply email: one ASCII email address, at most 254 characters; mailbox lists and header-control characters are rejected.
- Subject: 1–120 characters; one line.
- Message: 10–3,000 characters; line breaks are allowed, unsafe control characters are rejected.
- Unknown fields and object/array payloads are rejected. Validation is shared by the client and server; client validation is not the security boundary.
- Cross-site origins, cross-site fetches, missing request markers and non-JSON writes are rejected before sending.
- Per-process limits: **5 requests per IP per 15 minutes**, **10 per username per hour**, and **100 total per hour**. Invalid and failed submissions consume limits too. Rate-limit responses include retry guidance.
- A hidden honeypot silently drops filled submissions with a generic response. It supplements the limits; it is not an authentication mechanism.
- Connection, greeting, socket and DNS timeouts bound stalled transport activity. The submit button and fields are disabled while sending. Failures keep the draft, while success clears it. A client timeout warns that delivery could not be confirmed rather than claiming definite failure.

These counters use in-memory stores, so restarting the API resets them. A multi-instance deployment needs shared rate-limit storage and the correct trusted proxy configuration. Email ownership verification and guaranteed delivery receipts are outside this implementation; Gmail limits and filtering still apply. The current real test reached Inbox, but future messages may be filtered differently.

## Re-run commands

```sh
npm test
npm run verify:rendering
npm run build
npm run verify:mail
```

`verify:mail` authenticates without sending email. `--starttls` tests port 587 without changing `.env`. It prints sanitized status only.

For browser QA, run `npm run qa:contact`. It serves the current build with two temporary Atlas accounts, isolates the normal session cookie and captures mail locally using Nodemailer. The ignored `.polish-qa-control` file accepts `contact-ready`, `contact-fail`, `contact-slow`, `contact-count` and `cleanup`, plus the existing content/image modes. Finish with `cleanup` so the records are removed and the process exits. The local capture is test evidence, not real delivery evidence.

Only after explicit approval for a real outgoing test message, with the local API running:

```sh
npm run verify:contact:delivery -- <username> --send
```

That command sends one message to the selected account's stored email through the normal API. It requires the explicit `--send` flag. Check the registered inbox and confirm receipt separately; do not repeat automatically if a timeout leaves delivery uncertain.
