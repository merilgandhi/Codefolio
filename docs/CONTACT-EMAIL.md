# Public contact form and Gmail API delivery

Both public portfolio layouts include a **Contact** navigation link and the same responsive React Hook Form contact section. Earlier SMTP-based checks confirmed the branded message arrived in Gmail. The deployed Render Free service uses a Gmail OAuth-over-HTTPS code path because SMTP is blocked, but production OAuth credentials and a delivery check have not been completed; production contact and password-reset email delivery remain unverified. Nodemailer composes the MIME email in both paths, and its stream transport hands the production message to Gmail's API.

## Request flow and privacy

1. A visitor supplies their name, reply email, subject and message on `/:username`.
2. `POST /api/contact/:username` checks request origin/marker, JSON format, limits and validated fields.
3. The backend validates the username and queries MongoDB for that account's private registered email. Request bodies cannot supply `to`, `from`, envelopes, attachments or account selectors.
4. The Gmail API sends from the configured owner Gmail account to that one saved recipient. The visitor's address is used as **Reply-To**, so the owner can reply directly.
5. The API returns a generic success only after Gmail accepts the message. A provider error produces a sanitized 503 response. API acceptance does not by itself prove inbox receipt; confirm the message in Gmail when checking delivery.

The public document, public JSON and contact responses do not expose the owner's email, OAuth settings or provider error details. Messages contain branded HTML generated by the server and a complete plain-text alternative. Visitor content is escaped before insertion into the HTML. Each message has a single recipient. A visitor's name/email/subject/message is transmitted to the chosen portfolio owner; the form explains this before submission. Contact messages are not stored in MongoDB or logged by the production transport.

The form appears only on the public page. Private draft previews do not contain a sending form or a broken Contact anchor. Saved portfolio data and the owner's session are unchanged by this milestone.

## Email design

`server/mail/contactEmail.js` renders the HTML and text versions. The HTML uses a CodeFolio wordmark, muted violet accents, a prominent subject, sender initials/name/address, a separate message card, a reply button and a compact portfolio footer. Paragraphs and line breaks are preserved without truncating the message. The reply button encodes the validated visitor address and subject; the normal email Reply action also works through Reply-To.

The self-contained email uses presentation tables, inline styles and a mobile media query, with no external fonts, images or tracking assets. Its card is capped at 640px and adapts to a narrow reading pane. Gmail's supported styles and media queries are documented in [Google's CSS reference](https://developers.google.com/workspace/gmail/design/css).

Browser previews passed at 320, 390, 760 and 1280px with no horizontal overflow. The owner confirmed the actual new message had the branding, message card and reply button and looked good in Gmail. Other email applications have not been manually checked; their rendering may differ. The plain-text alternative is retained for clients that do not display HTML.

Run `npm run preview:email` for a fictional enquiry preview without sending any mail. It writes generated HTML/text under the ignored `artifacts/email-preview/` directory and serves the HTML at a printed loopback URL. Ctrl+C stops that preview server. ## Gmail OAuth setup

Production sends through Gmail's HTTPS API, which works from Render Free. The OAuth client requests only `https://www.googleapis.com/auth/gmail.send`; Google classifies this as a sensitive scope. The sender signs in and grants that permission to the CodeFolio mailer. The refresh token stays server-side and is never sent to the browser.

1. In Google Cloud Console, create a project and enable **Gmail API**.
2. Configure the OAuth consent screen as an external app and add only the `gmail.send` scope. Set its publishing status to **In production** before generating a token. External apps left in **Testing** issue refresh tokens that expire after seven days.
3. Create an OAuth client ID with application type **Desktop app**.
4. In the ignored local `.env`, set `GMAIL_USER` to `merilgandhi2203@gmail.com`, then add the OAuth client ID and client secret as `GMAIL_CLIENT_ID` and `GMAIL_CLIENT_SECRET`.
5. Run `npm run gmail:oauth`. Open the printed Google URL, sign in to the sender account, and review the Gmail send permission. When you approve, the local callback saves `GMAIL_REFRESH_TOKEN` to `.env` without printing it.
6. An unverified-app warning may appear for personal use; Google allows a small known user group to proceed without verification, while wider distribution may require verification. See [Google's refresh-token rules](https://developers.google.com/identity/protocols/oauth2) and [Gmail scope guidance](https://developers.google.com/workspace/gmail/api/auth/scopes).
7. In Render, add `GMAIL_USER`, `GMAIL_CLIENT_ID`, `GMAIL_CLIENT_SECRET` and `GMAIL_REFRESH_TOKEN`. Set `GMAIL_FROM` only if needed, and make it match `GMAIL_USER`. Remove the old `SMTP_*` variables after this configuration is ready.

Never paste OAuth secrets or refresh tokens into chat or commit them. The setup helper binds only to loopback, checks OAuth state, uses PKCE, and writes the refresh token to the ignored `.env` file. Local development may still use Nodemailer SMTP; production never falls back to SMTP.

## Validation and abuse controls

- Name: 1–100 characters; one line.
- Reply email: one ASCII email address, at most 254 characters; mailbox lists and header-control characters are rejected.
- Subject: 1–120 characters; one line.
- Message: 10–3,000 characters; line breaks are allowed, unsafe control characters are rejected.
- Unknown fields and object/array payloads are rejected. Validation is shared by the client and server; client validation is not the security boundary.
- Cross-site origins, cross-site fetches, missing request markers and non-JSON writes are rejected before sending.
- Per-process limits: **5 requests per IP per 15 minutes**, **10 per username per hour**, and **100 total per hour**. Invalid and failed submissions consume limits too. Rate-limit responses include retry guidance.
- A hidden honeypot silently drops filled submissions with a generic response. It supplements the limits; it is not an authentication mechanism.
- Gmail token-refresh and HTTPS API timeouts bound stalled transport activity. The submit button and fields are disabled while sending. Failures keep the draft, while success clears it. A client timeout warns that delivery could not be confirmed rather than claiming definite failure.

These counters use in-memory stores, so restarting the API resets them. A multi-instance deployment needs shared rate-limit storage and the correct trusted proxy configuration. Email ownership verification and guaranteed delivery receipts are outside this implementation; Gmail limits and filtering still apply. Earlier SMTP tests reached Inbox, but Gmail API delivery must be checked after OAuth is configured.

## Re-run commands

```sh
npm test
npm run verify:rendering
npm run build
npm run verify:mail
```

`verify:mail` checks an OAuth token refresh or local SMTP authentication without sending email. `--starttls` only affects the local SMTP fallback. It prints sanitized status only.

For browser QA, run `npm run qa:contact`. It serves the current build with two temporary Atlas accounts, isolates the normal session cookie and captures mail locally using Nodemailer. The ignored `.polish-qa-control` file accepts `contact-ready`, `contact-fail`, `contact-slow`, `contact-count` and `cleanup`, plus the existing content/image modes. Finish with `cleanup` so the records are removed and the process exits. The local capture is test evidence, not real delivery evidence.

Only after explicit approval for a real outgoing test message, with the local API running:

```sh
npm run verify:contact:delivery -- <username> --send
```

That command sends one message to the selected account's stored email through the normal API. It requires the explicit `--send` flag. Check the registered inbox and confirm receipt separately; do not repeat automatically if a timeout leaves delivery uncertain.
